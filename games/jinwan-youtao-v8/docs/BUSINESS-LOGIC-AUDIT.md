# 《今晚有套吗？》v8 经营逻辑审计与业务规则 v1

更新：2026-10-18。范围：`games/jinwan-youtao-v8/src/{core,state}/`。本文件是程序状态和玩家体验共同遵守的规则，仍需在真机完整体验后确认数值平衡。

## 1. 唯一经营主循环

```text
Day N · 08:00 晨会（暂停；锁定预订、预估房态、确定经营方向）
        |
        v [brief-start]
08:00–20:00 经营（时间推进）
  入住/离店 | 清洁/维修 | 库存/餐饮 | 事件 | 团队 SOP | 投资建设
        |
        v [首次跨越 20:00]
20:00 复盘（暂停；当日预测快照；不入房费）
        |
        v [evening-close]
20:00–24:00 夜间经营（继续履约、等待离店和施工完成）
        |
        v [首次跨越 24:00]
Day N 日结（暂停；房费、平台佣金、固定运营费用入账）
        |
        v [continue]
Day N+1 · 08:00 晨会（重置每日数据，保留跨日预订/客史/成长/施工）
```

晨会 / 复盘 / 日结由 `operations.ts` / `evening.ts` / `game.ts` 分工执行。
- `prepareMorning` 同一天不能重复生成确认预订。
- `captureEvening` 同一天只捕获一次快照，不提前入房费。
- `settle` 在午夜生成一次日报，并暂停游戏；`reportOpen` 时**所有经营命令冻结，仅允许 `continue`**，防止已结算后再花钱、领奖和遗漏账目。
- `nextDay` 只在完成日报时执行，日数据清零并保留跨日状态。

## 2. 房态及订单状态机

预订：`confirmed → arrived → checkedin`，或 `confirmed/arrived → lost`。失约的确认预订最多赔付 ¥600 一次；不能把同一个预订重复标记为 lost。

客房：
- `unbuilt → available`：新楼层验收后、玩家完成配置，才能出售。
- `available → reserved → occupied`：会员/SUA 锁房保持预订身份。
- `available/reserved → occupied → dirty → cleaning → available`：入住退房和翻房闭环。
- `available → maintenance → available`：维修 / 装修与可售状态互斥。
- 入住操作按实际状态判断，重复执行不得多收钱、二次占房或重复登记。
- 已确认订单的 `bookedRate` 不随当天挂牌价及赠送升套而改变。

需始终满足：一个在住房间恰好对应一位在住客人；一个在住客人只占用一个房间；SUA 锁房的预订 ID 必须真实存在且尚有效。纯函数 `gameInvariants` 可自动审计。

## 3. 资源与现金规则

- 执行支出遵循“校验条件 → 确认余额 → 扣费 → 修改状态 → 留日志”。无效、重复或条件不满足的指令不扣款。
- 可重复采购不等于重复点击漏洞：每次采购属于独立交易，库存达到上限就禁止继续购买；一次性奖励、入住、投诉结案、房间配置必须幂等。
- 早餐、酒廊采购：每单 ¥300 +50 份（现行实现限制最终库存不高于 160；接近上限时存在购买量少于 50 的经济设计边界，未来需统一 UI 提示）。
- 普通客基础餐饮需求 1 份，家庭型为 3 份；已购生日双人早餐的 2 份在购买时预留，从本次服务库存需求中抵扣。若不能满足**完整份数**则等待，不得记录为“用餐完成”或暗扣不足部分。
- 客房清洁 ¥90、人工维修 ¥180、部门主管首聘 ¥3,800、日工资随主管等级 × ¥180。房价、装修费和后续服务成本的具体值以经济模型为准。
- 现金变动应可与本日收支对账；日报“收入”目前包含客房、附加服务、日常任务奖和里程碑奖励，未来建议细分经营收入/奖励收入。
- 午夜扣除实际平台佣金和当日固定费用，可产生负现金；**这是当前保留的资金压力机制**，后续需设计欠费/破产体验，不能默默截断账目。

## 4. 主管与自动化

前厅：等待住客 → 搜索可用房 → 办理入住。客房：脏房 → 接单前往 → 清洁后可售。工程：故障房 → 支付维修成本 → 接单前往 → 恢复房态。餐饮：低库存 → 支付补货成本 → 到场入库。收益主管：价格建议与定期巡场。

同一工作目标不能重复派单；员工必须抵达后工作并完成倒计时。任务结束后同步房态、库存、事件和进度。主管工作与玩家手动执行使用相同的经营命令及状态校验。

## 5. 成长和奖励

- 新档五步带教：晨会、入住、翻房、早餐采购、客房主管聘任；章节检验分阶段解锁装修、设施、活动与扩建。
- 新手带教门槛属于正式玩法；经营专项测试通过 `newGame({guided:false})` 测试已解锁阶段，新手专项测试仍运行完整五步解锁。
- 成长认证先达成计数器，再预约次日实际检查；失败保留进度、重约不产生重复支出。
- 日任务最多领取一次，阶段奖金和尾款之和不得超过标示奖金额；长期里程碑只能领取一次。
- 已到账的里程碑奖励同步进入日报收入，保证现金流水可以对账。

## 6. 存档

沿用原有 `schemaVersion=8` 和 `SAVE_KEY`，新增逻辑不得清空旧进度或依赖首次运行才有的字段。存档从完整状态恢复：已订预订、入住住客、员工任务、未完施工、跨日里程碑、阶段奖金等必须保持一致。存档无法读取时暂停新实例，不覆盖原存档。

## 8. 自动验收门槛

`npm test`、`npm run build` 必须全部成功；此外测试还需证明：
1. 同一订单不重复赔付、同一房间不重复入住、同一里程碑不重复领奖。
2. 房态/住客 ID、SUA 锁房、库存非负、任务奖金、现金数字均满足不变量。
3. 经营至少连续跨过两个营业日，晨会、20:00 复盘、24:00 日结各触发一次。
4. 20:00 快照不重复入账；24:00 结算后不可再操作；次日继续恢复执行。
5. 出现库存不足时服务不成功，补齐后才消耗库存并产生正向体验。

本 PR 不擅自修改房价、需求曲线、工资费率或广告体系。数值平衡需要另行安排长期模拟与真人试玩。
